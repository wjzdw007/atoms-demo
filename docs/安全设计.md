# 安全设计

这个应用的特殊之处在于：它会把**模型写出来的、不可信的代码**展示给用户，并且对公网开放、背后挂着按量计费的模型密钥。下面按威胁逐条说明现在是怎么防的，以及还有哪些没防住。

上线前请了一个独立的评审智能体（Claude Opus）通读代码做安全评审，下面标注「评审发现」的条目是它找出来、随后修掉的问题。上线后又做了第二轮评审，用隔离的复现用例确认了 8 个问题，标注为「第二轮评审」。第三轮评审通读全部代码，没有发现越权、注入或密钥泄露，找到的主要是能让单台服务器停摆的资源问题，标注为「第三轮评审」。

## 1. 生成的代码能不能攻击服务器

不能，因为服务端**从不执行**生成的代码。

- 模型的输出只被当作字符串：存进数据库，再原样发给浏览器。没有 `eval`、没有子进程、没有服务端渲染生成的页面。
- 智能体没有任何工具：不能读写文件、不能发网络请求、不能执行命令。提示词注入最多只能改变"生成出来的网页长什么样"，而这个网页只在发起请求的用户自己的浏览器里运行。
- 用户输入不会变成文件路径、命令或要抓取的 URL；所有 SQL 都是参数化的。
- 即便应用进程本身被攻破，线上的 systemd 服务也做了隔离（见 [deploy/atoms-demo.service](../deploy/atoms-demo.service)）：不能提权（`NoNewPrivileges`，所以碰不了 sudo）、文件系统只读（包括它自己的代码，靠 `ProtectHome=read-only`）、只能写数据库目录和构建缓存、读不到 SSH 密钥，并且只监听本机端口。

## 2. 生成的代码能不能攻击其他用户或本站

预览和分享页都把生成的代码放在 `sandbox="allow-scripts allow-forms allow-modals"` 的 iframe 里：

- 没有 `allow-same-origin`：它运行在一个不透明的源里，拿不到本站的 Cookie、localStorage 和 DOM。
- 没有 `allow-popups` 和顶层跳转：不能开新窗口，也不能把整个页面带走。
- 本站设置了 `X-Frame-Options: DENY` 和 `frame-ancestors 'none'`，不能被别的网站嵌进去做点击劫持。
- 宿主页只接受来自**这个 iframe 窗口对象**的消息，并且只认两种：保存数据、上报错误。恶意应用最多能改写"正在看它的这个用户在这个应用里的数据"，服务端还会把数据强制转成字符串表并限制大小。
- 标题、对话、作者名等用户或模型可控的文字全部由 React 转义输出，没有任何 `dangerouslySetInnerHTML`。

**第三轮评审：分享页可以被用来钓鱼。** 沙箱隔离的是本站的 Cookie 和数据，但生成的应用仍然可以联网，也可以把自己所在的 iframe 跳到别的页面，而地址栏显示的始终是本站域名。分享页现在在应用上方固定显示一行提示：内容由用户生成、与本站无关，不要在其中输入密码、验证码或支付信息。没有用 CSP 禁止应用联网：查询公开接口（天气、汇率）是这类应用的正常需求，一刀切会把它们一起禁掉（见文末「还没防住的」）。

**上线后发现：生成的应用卡死会连累本站页面。** 一个生成的国际象棋应用里有死循环（推进一格的那行代码写在了循环外面），走到第二步就永远停不下来。沙箱挡得住它读本站的数据，挡不住它占着线程：在把沙箱 iframe 和页面放在同一个进程里的浏览器中，整个标签页会跟着卡死；而且卡死不会产生报错，"让智能体修复"也接不住。现在有两层保护：

- **循环保护**：应用展示之前，脚本里的每个循环体开头都被插入一次检查（用 acorn 解析后按语法树插入，不是字符串替换；只改展示的副本，保存的代码不变，行号也不变）。一个循环连续占用线程超过 4 秒就抛出错误中止，于是死循环变成一条普通的运行时错误，可以一键交给智能体修复。会让出线程的循环（`await`、定时器驱动的游戏循环）不受影响。这一层不依赖浏览器的进程模型。
- **无响应检测**：宿主页每 2 秒问应用一次"还在吗"，8 秒没有回音就把 iframe 移除（这才真正停掉失控的代码），换成一条提示和"重新运行"按钮。它兜住循环保护管不到的情况（`new Function`、内联事件属性里的代码、解析不了的脚本），但只在浏览器把沙箱 iframe 放在独立进程时有效（Chromium 是这样）。

**评审发现：表单型 CSRF。** 沙箱里的应用可以提交表单，别的网站也可以用 `text/plain` 表单伪造 JSON 请求。现在 [src/proxy.ts](../src/proxy.ts) 对所有非 GET 的接口请求校验 `Origin`：必须等于本站；沙箱发出的 `Origin: null` 一律拒绝。

## 3. 用户之间的越权访问

- 每个项目相关的接口都先用会话里的用户 ID 调 `getOwnedProject(id, userId)`；不属于自己的项目一律返回 404（不泄露是否存在）。
- 版本按 `(project_id, id)` 查询，订单和积分按 `user_id` 查询。
- 生成的应用的数据主键是 `(project_id, user_id)`，`user_id` 只取自会话。别人发布的应用，登录用户可以用，但读写的是自己那一份。
- 后台任务只对发起它的用户可见：查看进度、取消都要求任务的 `userId` 与会话一致。

**第二轮评审：同一浏览器换账号会串数据。** 生成的应用的数据在浏览器里有一份本地副本，原来只按应用区分。退出登录后，下一个使用这个浏览器的人仍能看到上一个账号的数据；如果他自己的云端数据是空的，这份旧数据还会被自动上传到他的账号下。现在本地副本按「查看者 + 应用」区分（查看者是服务端返回的用户 ID，未登录时是匿名），只会把同一个查看者自己的副本补传到云端，退出登录时清空全部本地副本。

评审对这一项的结论是没有发现越权路径。

## 4. 账号与会话

- 会话是 `jose` 签名的 JWT，放在 httpOnly、SameSite=Lax、仅 HTTPS 的 Cookie 里；生产环境缺少 `AUTH_SECRET` 会拒绝启动签名。
- 登录只支持 Google，本站不保存任何密码，也就没有密码泄露、撞库和弱口令的问题。
- 发起登录按 IP 限流；访客账号的创建也按 IP 限流。
- Google 登录走授权码流程：随机 `state` 存在 httpOnly Cookie 里并在回调时比对，服务端换取令牌，校验 ID Token 的签发者、受众和 `email_verified`。

**第三轮评审：账号按邮箱认人。** Google 登录原来用邮箱匹配本站账号，邮箱被改名或被回收给别人之后，新主人会登录进原主人的账号。现在账号绑定的是 Google 的账号标识符（`sub`，不会变也不会重新分配），数据库里一个标识符只能对应一个用户；旧账号在下次登录时按邮箱找到并绑定一次。邮箱已经绑定了另一个 Google 账号时拒绝登录。

**第三轮评审：会话 Cookie 可以被兄弟站点覆盖。** 同一父域名下的其他站点可以给本站种 Cookie，把自己准备好的会话塞进访问者的浏览器。HTTPS 下 Cookie 现在使用 `__Host-` 前缀（会话和 OAuth 的 `state` 都是）：浏览器只接受本站自己设置、带 Secure 且不带 Domain 的这个名字。改名之前签发的旧会话在过期前继续有效，不会把所有人踢下线；改名之后签发的令牌只认新名字。

**评审发现：账号预占。** 评审时还有邮箱密码注册，且不验证邮箱归属：攻击者可以先用受害者的邮箱注册，等受害者用 Google 登录进入这个攻击者也能登录的账号。当时的修复是首次 Google 登录时清除原密码并作废旧会话；之后邮箱密码登录被整体移除，这类问题从根上不存在了（那段清理逻辑保留着，用于处理移除前留下的旧账号）。

**第二轮评审：访客升级为正式账号时会话没有轮换。** 访客第一次用 Google 登录时账号原地升级，但原来的访客令牌照样有效：如果这个令牌之前泄露过，或是被人事先塞进浏览器的，它就跟着升级得到了正式账号的权限。现在升级时版本号加一并重新签发 Cookie，旧令牌立即失效。

**第二轮评审：登录已有账号后访客项目不见了。** 访客做了项目之后登录一个已经存在的 Google 账号，会话直接切到那个账号，访客的项目留在原来的访客身份下，再也够不着。现在登录时把访客的项目和应用数据并入该账号（同一个应用两边都有数据时保留账号自己的），访客身份的会话随之作废。

**评审发现：会话无法撤销。** 原来退出登录只是删 Cookie，被盗的令牌 30 天内仍然有效。现在用户表有 `session_version`，令牌里带着签发时的版本号；退出登录或凭据变更会让版本号加一，旧令牌立即失效。

## 5. 费用与额度

模型按量计费，所以"别人能不能白用我的密钥"是一类安全问题。

- 模型密钥只在服务端读取，构建产物里不含；用户能选的模型来自服务端白名单，客户端传别的名字会被忽略。
- 每次生成先扣额度再启动任务。免费次数和积分的扣减各是**一条带条件的 SQL**，并发请求不可能把最后一次额度花两遍，余额也不会变负。
- 订单结算在一个事务里完成，同一笔订单并发确认五次也只发放一次积分。
- 全站每日生成次数有硬上限，用独立的计数表记录，只增不减。

**评审发现：退款可被用来无限白嫖。** 原来任何失败都退还额度，包括"模型没有返回网页"和超时。攻击者可以让模型输出纯文本（照样能在代码页看到全部内容），任务失败后额度退回，无限重复；而且退款还会把全站上限的计数一起减回去。现在只有**模型服务方出错**才退款；请求自身能造成的结果（没有可用的网页、输出过大、取消、到达总时长上限、竞速里主动不再等的那一路）都不退。模型卡住（超过 120 秒没有任何输出，连思考内容都没有）算服务方出错，会退款；这种情况下用户同样拿不到任何输出，所以不能用来白嫖。全站计数也改成了不受退款影响的独立计数。

**评审发现：积分上限可绕过。** 余额上限只在下单时检查，攻击者可以先攒一批未支付订单再逐个确认。现在每个账号同时只保留一笔未支付订单，结算时再检查一次上限。

**第二轮评审：并发下单和结算仍能越过上限。** 上面两项检查都是"先读再写"，发生在事务之外，同时发出的两个请求各自都能通过。现在"一个账号只有一笔未支付订单"是数据库的唯一索引；余额上限写在把订单标为已支付的那条语句的条件里，和发放积分在同一个事务中。

**第二轮评审：失败的竞速请求能耗尽全站额度。** 竞速要给每个模型各扣一次额度，其中一个扣不到（比如积分不够）时，前面已扣的会退给用户，但全站每日计数和访客的 IP 共用额度没有放回。于是一批注定失败的请求不启动任何任务，就能把全站当天的额度占满。现在区分两种情况：任务没有启动的"预留"会连同全站计数和 IP 额度一起释放；任务跑过之后的退款仍然不动全站计数。

**第三轮评审：评审阶段出错会白送一份代码。** 工程师写完之后，评审或修复阶段只要模型服务出错（限流很常见），整个任务就算失败并退款，而完整的代码已经推送到了页面上。现在评审和修复都只是加分项：它们失败时保留工程师的版本照常保存，并在对话里注明"未经评审"，既不丢成果也不退款。

**自助到账等于免费发积分。** 最初的"演示支付"让用户自己点一下就到账，线上开着它就是无限白嫖。现在默认关闭购买；线上用 `manual` 模式：用户只能下单，积分要等管理员通过带令牌的管理接口确认收款后才发放。管理接口用常数时间比较令牌，未配置令牌时整个接口返回 404。自助到账的 `mock` 模式只保留给本地演示。

另外加了：单账号每日生成总上限（免费加付费）、每个用户和全服务器的并发任务上限。

**访客按 IP 共用额度。** 访客身份只是一个 Cookie，清掉就能换一个新的。所以访客的免费次数除了按账号算，还按来源 IP 共用一个每日额度池（存的是 IP 的带密钥哈希，不存明文）。登录用户的身份由 Google 证明，不受这个池子限制。代价是同一个出口 IP 下的多个真实访客会互相占用额度。

## 6. 资源耗尽

- 请求体由 nginx 限制在 2MB；需求文本截断到 4000 字。
- 存储配额和单个版本的大小都按字节计算（第二轮评审发现原来统计的是字符数，中文内容会被少算到三分之一），保存新版本时再校验一次账号的总配额。
- 流式输出一旦超过单个版本的大小上限就中止，这同时限制了任务事件日志占用的内存。转发给页面的思考内容每次模型调用最多 6 万字，超出的部分不再转发。
- 一次模型调用超过 120 秒没有任何输出就放弃；每个任务另有 30 分钟的总时长上限。每个用户同时最多跑 2 个任务，全服务器最多 8 个。
- 每个项目保留有限数量的版本；每个账号的项目数、版本总字节数、保存了数据的应用数都有上限。

**第三轮评审：应用数据可以免费写满磁盘。** 生成的应用保存的数据原来不计入账号的存储配额，保存接口也不限流；访客可以免费建几十个空项目，每个写满 500KB，再换一个访客身份重来，不消耗任何生成额度。现在应用数据和版本一起计入账号配额，访客的配额是正式账号的五分之一，保存接口和新建项目按用户限流；访客合并进正式账号时不能越过项目数上限；Cookie 已过期、再也登录不了的访客账号（没有公开分享过应用的）连同数据每天清理一次。

**第三轮评审：进度流可以撑爆内存。** 每个查看进度的连接都会拿到任务的全部事件，原来是一次性塞进连接的缓冲区，连接数也没有上限：开几百个连接而不读取，每个连接就在内存里压一份完整的日志，进程会被内存上限杀掉，所有人正在跑的任务随之中断。现在只在对方读取时才按批发送，一个不读的连接最多占一批；每个任务同时最多 6 个连接。

**第三轮评审：一段正则可以卡住整个服务。** 检查脚本语法前要先从文档里找出 `<script>` 段，原来的正则遇到大量不闭合的 `<script>` 会反复扫到文档末尾：800KB 的输入实测阻塞 10 秒，期间 Node 不响应任何请求。现在改成从左到右只扫一遍，同样的输入在 1 秒内完成，并有测试守着。

**第三轮评审：请求体大小只靠 nginx。** 应用自己读取 JSON 时不设上限，前面一旦没有 nginx（或没配上限），一个超大请求就会被整个读进内存。现在所有接口都通过带上限的读取函数取请求体（默认 32KB，应用数据接口按配置放宽）。

**第三轮评审：安装脚本不校验下载的 Node。** `setup.sh` 原来把下载内容直接解压。现在先校验 SHA-256：默认版本的校验值写在脚本里（取自 nodejs.org），换版本时用 `NODE_SHA256` 指定。

**评审发现：恢复和 Remix 可以免费复制大文档。** 这两个操作不消耗额度却会复制整份 HTML，可以用来填满磁盘。现在它们按用户限流，并且计入账号的存储配额。

## 7. 密钥与仓库

- `.env*`（除 `.env.example`）和数据库目录被 git 忽略，密钥从未进过提交历史。
- 所有配置只在服务端模块里读取，没有任何客户端组件引入它们。
- 服务器上的 `.env.local` 权限为仅属主可读。

## 还没防住的

- **限流和任务都在单进程内存里**。重启会清空限流计数，也会打断运行中的任务（额度在下次启动时自动退还）。关闭任务记录和退款写在同一个事务里：不会退两次；退款写入失败时任务记录保持未关闭，下次启动再退（第二轮评审发现原来是先关闭、后退款，第二步失败就永远漏退）。
- **有足够多 IP 的攻击者仍可以耗尽全站每日额度**，让其他人当天无法生成。上限保护的是账单，不是可用性。
- **收款确认是人工的**：没有接支付渠道，管理员确认订单靠的是线下核对。管理令牌泄露等于可以任意发积分，需要像密钥一样保管。
- **同一父域名下的其他站点**（`*.smallway.cn`）在浏览器看来与本站"同站"，SameSite Cookie 对它们不设防；跨站请求由 Origin 校验拦截，种 Cookie 由 `__Host-` 前缀拦截。
- **分享出去的应用可以联网**。它拿不到本站的任何东西，但可以把访问者在这个应用里输入的内容发到别处，也可以伪装成登录页。现在只有分享页上的提示在防这件事；要根治需要把分享页放到独立域名，或者提供"禁止联网"的开关。
- **不经过循环的卡死在部分浏览器里仍会卡住页面**。循环保护覆盖了脚本里写出来的循环；用 `new Function`、`eval` 或内联事件属性执行的代码不在其中，这类卡死要靠无响应检测，而它在把沙箱 iframe 和页面放在同一进程的浏览器里起不了作用。要彻底隔离，需要把预览放到独立的站点域名下。
- **数据库没有外键**。删除项目是一个事务，迟到的对话消息也不会写进已删除的项目，但表之间的引用关系靠代码维持，不是数据库保证的。
- 自动化测试覆盖了额度、订单、退款、版本号、数据归并、存储配额、访客清理、进度流的连接上限和脚本扫描的耗时；登录流程、会话轮换、Cookie 改名的过渡、评审失败时的降级和浏览器里的本地副本隔离没有自动化测试。
