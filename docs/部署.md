# 部署与运维

应用是一个需要长期运行的 Node 进程：生成任务在进程内后台执行，所以只能部署成**单个实例**，不适合函数会在响应后被冻结的 Serverless 平台，也不要开多个副本。

三种部署方式，任选其一：

| 方式 | 适合 | 入口 |
| --- | --- | --- |
| 一键安装到云服务器 | 一台全新的 Ubuntu / Debian 服务器 | [scripts/setup.sh](../scripts/setup.sh) |
| Docker | 已经有容器环境 | [Dockerfile](../Dockerfile)、[docker-compose.yml](../docker-compose.yml) |
| 手动安装 | 其他发行版，或想自己掌握每一步 | 本文「手动安装」 |

> 验证范围：发布脚本（构建、切换、健康检查、失败回滚、手动回滚、备份）在本机用临时目录完整跑过；`setup.sh` 在一台 Ubuntu 24.04 服务器上跑过「从旧布局迁移」这条路径（Node、目录、systemd 沙箱、sudoers、备份定时器、发布）。还没在真实环境跑过的是：`setup.sh` 里安装 nginx 和申请证书的那一段，以及 Docker 镜像。第一次用到时请留意输出。

## 一键安装

前提：

- 一台 Ubuntu 22.04+ 或 Debian 12+ 服务器，1 GB 以上内存。
- 能用 SSH 登录的**普通用户**，并且有 sudo 权限（不要用 root，应用不应该以 root 运行）。
- 想要 https 的话：一个已经解析到这台服务器的域名，80 和 443 端口对外开放。

在自己的电脑上，进入本仓库执行：

```bash
DEPLOY_HOST=my-server DOMAIN=atoms.example.com EMAIL=me@example.com ./scripts/setup.sh
```

`DEPLOY_HOST` 是 SSH 主机名（`~/.ssh/config` 里的别名或 `user@host`）。跑完后站点就已经在线，处于演示模式（用内置模板走完整个流程）。接下来填上模型密钥：

```bash
ssh my-server
nano ~/atoms-demo/shared/.env.local     # 填 LLM_API_KEY，其余选项见 .env.example
sudo systemctl restart atoms-demo
```

可选参数（都是环境变量）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DOMAIN` | 无 | 域名。不给就不装 nginx，应用只监听 `127.0.0.1:3100`，由你自己的反向代理接入 |
| `EMAIL` | 无 | Let's Encrypt 的联系邮箱，给了 `DOMAIN` 就必填。传入即表示同意 Let's Encrypt 的订阅协议 |
| `PORT` | `3100` | 应用监听的本机端口 |
| `NODE_VERSION` | `24.14.0` | 安装到 `~/atoms-demo/node` 的 Node 版本 |
| `NODE_MIRROR` | `https://nodejs.org/dist` | Node 下载地址。服务器在中国大陆时用 `https://npmmirror.com/mirrors/node` |
| `NPM_REGISTRY` | `https://registry.npmjs.org` | 服务器上构建时用的 npm 源。中国大陆用 `https://registry.npmmirror.com`。会记在服务器上，之后每次发布沿用 |
| `SETUP_ONLY=1` | 关 | 只准备服务器，不发布 |

脚本可以重复执行，每一步都会先检查现状。它在服务器上做的全部改动：

1. 把 Node 解压到 `~/atoms-demo/node`（不影响系统里已有的 Node）。
2. 建立目录 `~/atoms-demo/{shared,releases,backups}`。
3. 生成 `~/atoms-demo/shared/.env.local`（权限 600），里面有随机的 `AUTH_SECRET`。已有的文件不会被改动。
4. 安装三个 systemd 单元：`atoms-demo.service`（应用，带沙箱限制）、`atoms-demo-backup.service` 和 `.timer`（每天备份数据库）。
5. 写入 `/etc/sudoers.d/atoms-demo`：只允许当前用户免密执行 `systemctl restart|start|stop atoms-demo`，发布脚本靠它重启服务。
6. 给了 `DOMAIN` 时：安装 nginx 和 certbot，申请证书，写入 `/etc/nginx/sites-available/atoms-demo`。如果 nginx 里已经有这个域名的站点，这一步整个跳过。

### 目录布局

```
~/atoms-demo/
  node/               Node 运行时
  shared/.env.local   密钥与配置，所有版本共用
  shared/deploy.env   这台服务器的发布设置（npm 源、端口）
  shared/data/        SQLite 数据库
  releases/<编号>/    每次发布一个目录，保留最近 5 个
  current             指向正在运行的那个版本的软链接
  backups/            数据库备份
```

## 发布新版本

```bash
DEPLOY_HOST=my-server ./scripts/deploy.sh
```

发布的是**最后一次提交**（没提交的改动不会带上，脚本会提醒）。过程：

1. 把代码上传到一个新的 `releases/<时间>-<提交号>/` 目录，在那里 `npm ci` 和构建。此时线上版本照常服务；构建失败只会删掉这个新目录。
2. 备份数据库。
3. 如果有正在运行的生成任务，最多等 300 秒让它们跑完（`DRAIN_SECONDS` 可调，`0` 表示不等）。
4. 把 `current` 指向新版本并重启服务。
5. 轮询 `/api/health`，40 秒内不健康就自动切回上一个版本并报错退出。

重启时仍在运行的生成任务会被中断。应用下次启动时会自动把这些任务的额度退还，并在对应项目的对话里留一条说明。

### 回滚

```bash
DEPLOY_HOST=my-server ./scripts/deploy.sh --rollback
```

切回当前版本之前的那一次发布并重启。回滚只换代码，**不动数据库**。数据库迁移都写成了向前兼容的（见 [src/lib/db.ts](../src/lib/db.ts) 里的说明），所以旧代码可以直接跑在新库上；真要把数据也退回去，按下面「恢复」操作。

## Docker

```bash
cp .env.example .env.local      # 填 AUTH_SECRET（openssl rand -hex 32）和 LLM_API_KEY
docker compose up -d --build
```

应用发布在本机的 `127.0.0.1:3000`，数据库在名为 `atoms-data` 的卷里。对外提供服务时在前面放一个 https 反向代理（可参考 [deploy/nginx.conf.example](../deploy/nginx.conf.example)，注意关闭响应缓冲）。只想先用 http 试一下，需要在 `.env.local` 里加 `ALLOW_HTTP=1`，否则登录 Cookie 不生效。

升级：`git pull && docker compose up -d --build`。备份：

```bash
docker compose exec atoms node scripts/backup.mjs /app/data/backups
```

## 手动安装

一键脚本做的事，手动做是这几步（以用户 `ubuntu` 为例）：

1. 把 Node 22 或更新的版本解压到 `~/atoms-demo/node`。
2. `mkdir -p ~/atoms-demo/{shared/data,releases,backups}`，把 `.env.example` 复制成 `~/atoms-demo/shared/.env.local` 并填写，`chmod 600`。生产环境必须填 `AUTH_SECRET`。
3. 把 [deploy/](../deploy) 下的 `atoms-demo.service`、`atoms-demo-backup.service`、`atoms-demo-backup.timer` 复制到 `/etc/systemd/system/`，改掉里面的用户名、路径和端口，然后 `sudo systemctl daemon-reload && sudo systemctl enable atoms-demo atoms-demo-backup.timer`。
4. 让部署用户可以免密执行 `sudo systemctl restart atoms-demo`（`/etc/sudoers.d/` 下加一条规则）。
5. 按 [deploy/nginx.conf.example](../deploy/nginx.conf.example) 配置 nginx，用 certbot 的 webroot 方式申请证书。
6. 在自己的电脑上执行 `DEPLOY_HOST=<主机> ./scripts/deploy.sh`。

Google 登录是可选的：在 `.env.local` 里填 `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET` 和 `APP_URL`，并在 Google Cloud 里登记回调地址 `<APP_URL>/api/auth/google/callback`。服务器访问不了 Google 时，可以按 [deploy/google-relay.service.example](../deploy/google-relay.service.example) 用一条受限的 SSH 端口转发做中转。

## 从旧布局迁移

早期版本把代码、配置和数据都放在 `~/atoms-demo/app`。迁移到现在的布局只需要再跑一次 `setup.sh`（参数和首次安装一样；服务器在中国大陆记得带上 `NODE_MIRROR` 和 `NPM_REGISTRY`）。它会：

1. 停掉服务，把 `app/.env.local` 和 `app/data` **移动**到 `shared/` 下。
2. 换上新的 systemd 单元。
3. 接着执行一次发布，站点恢复。

从停服务到发布完成，站点会中断一分钟左右（实测 45 秒）。已有的 nginx 站点配置不会被改动。确认新版本正常后，可以删除 `~/atoms-demo/app`。

## 日常运维

### 状态与日志

```bash
systemctl status atoms-demo                 # 是否在运行
journalctl -u atoms-demo -f                 # 实时日志
journalctl -u atoms-demo -n 200 --no-pager  # 最近 200 行
curl -s http://127.0.0.1:3100/api/health    # {"ok":true,"jobs":0}
```

`/api/health` 在进程存活且数据库可读时返回 200，`jobs` 是正在运行的生成任务数；数据库读不了时返回 503。可以直接接到外部监控上。

### 备份与恢复

- 每天自动备份一次，每次发布前再备份一次，文件在 `~/atoms-demo/backups/atoms-<日期>-<时间>.db`，保留最近 30 份。
- 立刻备份一次：`sudo systemctl start atoms-demo-backup`。
- 备份用的是 SQLite 的 `VACUUM INTO`，应用运行中也能得到一致的副本。直接 `cp` 数据库文件得不到这个保证。
- 备份和数据库在同一台机器上，防不了磁盘损坏。重要数据请定期把 `backups/` 同步到别处。

恢复：

```bash
sudo systemctl stop atoms-demo
cp ~/atoms-demo/backups/atoms-<日期>-<时间>.db ~/atoms-demo/shared/data/atoms.db
rm -f ~/atoms-demo/shared/data/atoms.db-wal ~/atoms-demo/shared/data/atoms.db-shm
sudo systemctl start atoms-demo
```

### 修改配置

编辑 `~/atoms-demo/shared/.env.local` 后 `sudo systemctl restart atoms-demo`。配置在进程启动时读取，不重启不生效。全部选项见 [.env.example](../.env.example)。

### 升级 Node

带上新的版本号重跑安装脚本，再发布一次（原生依赖要用新 Node 重新安装）：

```bash
DEPLOY_HOST=my-server NODE_VERSION=24.15.0 SETUP_ONLY=1 ./scripts/setup.sh
DEPLOY_HOST=my-server ./scripts/deploy.sh
```

### 证书续期

certbot 自带的定时任务会自动续期，续期后自动重载 nginx。检查：`sudo certbot renew --dry-run`。

### 确认积分订单

`BILLING_MODE=manual` 时，管理员收到款后用管理接口确认订单，见 [接口.md](接口.md) 的「管理接口」。

## 排查

| 现象 | 原因与处理 |
| --- | --- |
| 发布时报 `shared/.env.local is missing` | 服务器还没准备好，或还是旧布局。先跑 `setup.sh` |
| 发布时 `sudo: a password is required` | 缺少免密重启的 sudoers 规则。重跑 `setup.sh`，或手动加上 |
| 服务起不来，日志里有 `AUTH_SECRET is required in production` | `.env.local` 里没有 `AUTH_SECRET` |
| 能打开页面，但登录后马上又变回访客 | 站点是 http 访问的。配好 https，或临时设 `ALLOW_HTTP=1` |
| 生成进度不是一点点出来，而是最后一次性出现 | 反向代理在缓冲响应。nginx 要设 `proxy_buffering off` |
| 生成中途断开 | 反向代理的读超时太短。nginx 的 `proxy_read_timeout` 要大于单次生成的最长时间（默认 600 秒） |
| 日志里有 `Could not recover interrupted jobs` | 启动时读不了数据库。检查 `shared/data` 的属主和 systemd 单元里的 `ReadWritePaths` |
